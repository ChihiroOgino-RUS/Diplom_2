# Diplom_2 — автотесты API для Stellar Burgers

Задание 2 второй части дипломного проекта «Автоматизатор тестирования на Java» (Яндекс Практикум): API-автотесты веб-приложения [Stellar Burgers](https://stellarburgers.education-services.ru/) с Allure-отчётом.

> ⚠️ На момент сдачи основной адрес приложения на технических работах, поэтому тесты выполняются на QA-адресе: `https://qa-stellarburgers.education-services.ru/` (константа `BASE_URL` в `ApiConstants`). Для переключения на прод достаточно поменять одну константу.

## Стек

- Java 11, Maven
- JUnit 4.13.2
- REST Assured 5.5.0 + Gson
- Lombok
- Allure 2.15.0

## Покрытые сценарии (12 тестов)

| Класс | Сценарии |
|---|---|
| `UserCreateTest` | создание уникального пользователя (200); создание уже зарегистрированного (403 «User already exists»); без name / без email / без password (403 «required fields») |
| `UserLoginTest` | вход существующим пользователем (200); вход с неверным паролем (401); вход с неверным логином (401) |
| `OrderCreateTest` | заказ с авторизацией и ингредиентами (200); заказ без авторизации (по заданию 401); заказ без ингредиентов (400); заказ с невалидным хешем (400) |

> ℹ️ **Известные расхождения QA-бэкенда с документацией** (проверено вживую 2026-10-23):
> - «Заказ без авторизации»: по документации ожидается 401 «You should be authorised», но QA-бэкенд не требует авторизацию для `POST /api/orders` и возвращает 200. Тест фиксирует требование (ожидает 401) и в текущем отчёте красный — расхождение эскалировано преподавателю.
> - «Невалидный хеш»: два корректных по форме, но несуществующих id возвращают 400 «One or more ids provided are incorrect» (в документации курса — 500; поведение обновлённого бэкенда подтверждено преподавателем). При смеси валидных и несуществующих id заказ создаётся — несуществующие id молча отбрасываются.
> - Валидные хеши QA отличаются от указанных в документации, поэтому тесты берут их динамически из `GET /api/ingredients`.

## Структура проекта

```
src/test/java/
├── client/StellarBurgersClient.java   — API-клиент: методы-шаги (@Step)
├── constants/ApiConstants.java        — BASE_URL и адреса эндпоинтов
├── model/                             — UserModel, UserCredentials, OrderRequest
├── tests/
│   ├── order/OrderCreateTest.java
│   └── user/UserCreateTest.java, UserLoginTest.java
└── utils/TestDataGenerator.java       — генерация уникальных тестовых данных
```

## Запуск тестов

```bash
mvn clean test
```

Тесты создают уникальных пользователей и чистят их за собой (`DELETE /api/auth/user` в `@After`).

## Allure-отчёт

Самый простой способ — готовый скрипт с закоммиченными результатами последнего прогона:

```bash
bash scripts/run-allure-report.sh
```

Отчёт откроется в браузере. Чтобы собрать отчёт из собственного прогона:

```bash
mvn clean test                                  # прогнать тесты
cp target/allure-results/* scripts/allure-results/   # обновить снимок результатов
bash scripts/run-allure-report.sh               # открыть отчёт
```
